# ContactSheet NSH 双平台重构计划

目标是在 macOS 和 Windows 上提供同一套相册管理与照片轮播体验，采用 NSH TSX 界面、Rust 应用核心和 SQLite 存储；macOS 额外支持 Apple Photos。本文是实施前的计划，本次只新增文档。

## 第一版范围

| 功能 | macOS | Windows |
| --- | --- | --- |
| 选择图片、导入文件夹 | 支持 | 支持 |
| 相册创建、重命名、删除、排序、封面 | 支持 | 支持 |
| 照片标题、说明、日期和地点编辑 | 支持 | 支持 |
| 独立展示窗口、顺序与随机轮播 | 支持 | 支持 |
| 菜单栏或系统托盘控制、关闭主窗口后继续播放 | 支持 | 支持 |
| 设置保存、窗口位置恢复、开机启动开关 | 支持 | 支持 |
| Apple Photos 相册浏览、授权与选择器 | 原生接入 | 不提供 |
| 旧版 SwiftData 数据导入 | 提供迁移入口 | 不直接读取 SwiftData |

初始验收设备定为 macOS 14+ Apple Silicon 与 Windows 11 x64。这是首批验证范围，其他系统版本和架构需要分别构建与验证。第一版不包含云同步、自动同步文件夹或跨设备相册同步。

本地导入默认复制图片到应用管理的媒体目录，记录相对路径。这样源文件移动后仍可播放，也为后续导出相册准备条件。Apple Photos 来源默认继续引用照片库，不批量复制原图。

## 当前实现与迁移对应

现有应用由 SwiftUI、AppKit、SwiftData、Photos 和 Combine 构成，核心代码集中在 `Sources/ContactSheet/`。

| 当前文件 | 迁移后的职责 |
| --- | --- |
| `App.swift` | Rust 启动入口、窗口生命周期、菜单和托盘 |
| `LibraryView.swift`、`ImportView.swift`、`DisplayView.swift` | NSH TSX 页面与组件 |
| `Playback.swift` | Rust 播放器及设置持久化 |
| `Models.swift` | Rust 数据访问层和 SQLite；Swift 模型保留给旧数据导出器 |
| `PhotoRepository.swift` | 共用本地媒体服务，加 macOS Photos 适配层 |
| `Tests/ContactSheetTests/ModelPlaybackTests.swift` | 保留作行为参考，将数据与播放规则覆盖迁到 Rust 测试 |

## 架构

```text
NSH TSX：相册窗口 / 导入界面 / 展示窗口 / 设置
                         │ 类型明确的命令与状态订阅
Rust：相册服务 / 单一播放器 / 图片任务 / 设置 / 桌面生命周期
              ├── SQLite + 应用媒体目录 + 缩略图缓存
              ├── 本地图片来源：macOS 与 Windows 共用
              └── macOS 适配：Swift Photos 桥接 / 旧数据导出
```

使用 NSH 官方支持的 Rust 与 TSX 混合方式，通过原生模块导出接口并生成 TypeScript 声明。TSX 管理选中项、编辑表单等局部界面状态；Rust 持有相册、播放状态和后台任务。不同窗口订阅同一份应用状态，播放器始终只有一个计时器。

建议目录为 `ui/`、`crates/contactsheet-core/`、`crates/contactsheet-desktop/`、`native/macos/` 与 `tests/fixtures/`。保持少量模块；平台差异集中在照片来源和系统集成处。

NSH 版本及源码提交在原型阶段固定，CLI、运行时和 API 使用同一版本。官方页面存在版本差异，具体调用以锁定版本的源码与可运行示例为准。

## 照片、存储与状态

SQLite 初步划分 `albums`、`assets`、`album_photos`、`annotations` 和 `settings`。照片使用应用自己的稳定 ID，来源信息另存为受管理文件或 Apple Photos 标识。相册与照片的关联保存顺序；说明属于照片，可由多个相册共享。删除相册只删除关联，保留共享照片和说明；不删除 Apple Photos 原图。

照片来源接口负责列举、元数据、图片请求、取消及变化通知。macOS Photos 功能通过 Swift 暴露窄 C ABI，再由 Rust 封装成异步接口。请求 ID、内存释放、主线程调用和回调生命周期需要在原型中验证。系统选择器可以保留原生 UI，但不得把整页相册业务继续留在 SwiftUI。

缩略图与展示图片按目标尺寸加载。解码在后台执行，限制并发和缓存容量；切换照片时取消旧请求，并核对请求版本，防止旧结果覆盖当前图片。图片不经 JSON/Base64 传输。优先验证 NSH 图片组件读取本地缓存文件；若不满足性能要求，再采用原生图片组件。

首批共用格式为 JPEG、PNG。对既有照片中的 HEIC 等格式，macOS 适配层应能生成展示资源；Windows 对未支持格式显示明确提示。原型阶段确定解码库和实际格式清单，不承诺两端天然支持所有格式。

共享状态变化带版本号，各窗口打开时先读取快照，再接收增量或更新通知。关闭主窗口只隐藏或销毁该窗口，应用和播放器继续运行；显式退出才停止任务并关闭进程。显示器拔出后，窗口恢复到当前可见区域。

## 旧数据迁移

1. 确认旧应用实际数据库、UserDefaults 和 Imports 目录位置，包含沙盒与非沙盒情况；迁移前备份，避免与运行中的旧应用同时修改数据。
2. 用原有 SwiftData 模型导出带格式版本的清单，包含相册 UUID、照片标识、排序、封面、说明及设置。通过系统接口读取，避免直接猜测 SwiftData 的 SQLite 表结构。
3. 在新数据目录中导入 SQLite 和已复制的媒体文件。保留源标识映射，以稳定 ID 或迁移记录去重；失败后可重试，不重复创建相册。
4. 比对相册数量、照片关联、顺序、封面、说明和文件校验值，抽查播放。无权限或已不存在的 Photos 项保留记录，并标记不可用。
5. 导入成功后才切换到新库。旧数据和旧客户端保留，便于回退；两版之间不做双向写入同步。

Windows 不直接读取 macOS Photos 标识。后续若需要把这些相册带到 Windows，需增加包含实际图片文件的导出与导入功能，这不属于本次首版同步范围。

## 实施阶段与完成条件

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 0 双平台原型 | 固定 NSH 版本；建立 Rust + TSX 工程；接入本地图片；验证双窗口、托盘及 Swift 桥接 | Mac 和 Windows 真机各启动一次打包应用，显示本地图片，控制同一播放器；Mac 额外读取一张 Photos 图片 |
| 1 数据与媒体核心 | SQLite、导入、缩略图、相册操作、说明、播放器与设置 | 使用临时库验证持久化、共享说明、排序、随机播放、空相册与取消行为；大图解码不阻塞界面 |
| 2 完整 NSH 界面 | 相册页、导入页、展示页、说明编辑和设置；桌面快捷键 | 两端完成导入、建相册、编辑、播放、关闭主窗口、托盘重开全过程 |
| 3 macOS 功能与旧数据 | Photos 浏览、系统选择器、权限恢复、旧数据迁移、开机启动 | 拒绝授权时仍可导入本地图片；迁移清单比对通过；失败重试不产生重复记录 |
| 4 发布与回归 | Windows 开机启动；两端打包、资源、权限、签名流程与升级数据保留 | 两端从产物安装启动，重启后恢复数据和设置；记录 UI、内存、后台运行与卸载行为 |

阶段 0 必须包含 Windows 原生构建与运行。当前会话只有已确认的 Mac 项目环境，Windows 机器或 CI 执行环境要在该阶段落实；交叉编译或 Mac 上的测试不能代替 Windows 验收。若依赖接入有缺口，先给出可复现问题与替代实现，再继续完整界面迁移。

## 验收重点

- 以现有测试中的相册去重、跨相册共享说明、排序、磁盘恢复、随机一轮不重复、空相册停止为核心行为基线。
- 两端测试中文和空格路径、损坏图片、导入取消、重复导入、照片丢失与数据库写入失败。数据库提交与文件复制之间使用暂存及恢复记录，避免留下可见但不完整的导入。
- 用固定的千张图片样本检查列表滚动、缩略图加载和快速切换；记录冷启动、首图耗时、内存峰值与闲置 CPU，原型建立基线后确定数值门槛。
- 检查播放时编辑或删除当前相册、随机播放后上一张、睡眠唤醒、多窗口状态一致性以及重复开关窗口不增加后台计时器。
- 在打包应用中验证 Photos 权限与沙盒文件访问。保留现有数据访问所需的应用身份，签名与权限变化单独验证。
- macOS 发布流程包含签名和公证；Windows 产物包含必要运行时与资源，正式分发签名取决于可用证书。明确区分本地可运行产物和已签名的发行产物。

## 开发与交付方式

当前项目文件均显示为未跟踪，实施前先确认仓库与基线状态，保护现有文件，再创建 `codex/nsh-cross-platform` 任务分支。旧 Swift 应用在新版通过验收前保持可构建。每个阶段单独提交，附运行方式、验证结果和剩余问题，界面迁移附截图。

第一项实际开发交付是阶段 0 的可运行原型及验证记录。此计划不预估固定工期，先用原型确认 NSH 桌面能力、Swift 桥接与 Windows 构建的实际成本。
